## 12. Streaming responses (SSE)
Code: [streaming-responses.py](../../01-backend/02-fastapi/12-streaming-responses/practice/streaming-responses.py)

- **What:** keep one HTTP response open and send pieces as they're produced. SSE = `content-type: text/event-stream`, each message `data: <text>\n\n`, optional `event: name`.
- **Why:** LLMs take seconds to finish. Streaming shows the first token in ~50 ms and makes the app feel instant. It's the backbone of every chat UI.
- **How:** an `async` generator yields SSE-formatted strings; return `StreamingResponse(gen, media_type="text/event-stream", headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"})`. End with a `done` event. Check `await request.is_disconnected()` and stop generating when the user leaves (saves money). Browser: `EventSource(url)` for GET, or `fetch` + `ReadableStream` for POST.
- **When:** LLM output, progress updates, long exports. Plain `StreamingResponse` (no SSE framing) works for big files/CSV.
- **Gotchas:** proxies buffer by default (disable it, or nothing arrives until the end). Once streaming starts the status is already 200, so report failures as an `error` event.

## 13. WebSockets
Code: [websockets.py](../../01-backend/02-fastapi/13-websockets/practice/websockets.py)

- **What:** one HTTP upgrade handshake, then a persistent connection where either side can send at any time.
- **Why:** SSE is server → client only. Chat, collaboration, multiplayer and voice/realtime agents need the client to send continuously too.
- **How:** `@app.websocket("/ws/{room}")`; authenticate **before** `ws.accept()` (browsers can't set headers, so use a query token or cookie) and close with code 1008 if bad; loop on `receive_text()`; catch `WebSocketDisconnect` and clean up; a `ConnectionManager` tracks sockets per room to broadcast.
- **When:** only when you need two-way. Otherwise use SSE (simpler, proxy-friendly, auto-reconnect).
- **At scale:** connection state lives in one process, so with several instances broadcast through Redis pub/sub. Add heartbeats (ping) and client reconnect logic.

## 14. Rate limiting
Code: [rate-limiting.py](../../01-backend/02-fastapi/14-rate-limiting/practice/rate-limiting.py)

- **What:** cap how often a client can call you. On excess: HTTP **429** + a `Retry-After` header.
- **Why:** stops abuse and brute-force logins, protects cost (every LLM call costs money), and keeps one noisy client from hurting everyone.
- **How:** **token bucket**: a bucket of `capacity` tokens refills at `rate`/sec, each request spends one. It allows bursts but enforces the average. Key by API key or user id (IPs are shared behind NATs and easy to rotate). Wire it as a `Depends()` on routes or routers. Inject a fake clock in tests instead of sleeping.
- **When:** every public endpoint, with tighter limits on login, signup and expensive LLM routes.
- **Other algorithms:** fixed window (simple, bursty at window edges), sliding window (smoother).
- **At scale:** in-memory only works for one process. Use Redis (atomic `INCR`/Lua) so all instances share counts; often also enforced at the gateway/CDN.

## Pick the right tool
| Need | Use |
|---|---|
| Stream LLM tokens to the browser | SSE |
| Chat room / live cursors / voice agent | WebSocket |
| Protect login + LLM endpoints | rate limit (429 + Retry-After) |
| Send a huge CSV without loading it in RAM | plain `StreamingResponse` |
