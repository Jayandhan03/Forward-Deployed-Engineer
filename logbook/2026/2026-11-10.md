## 1. Project layout
Code: [layered_app.py](../../01-backend/01-python-app-skills/01-project-layout/practice/layered_app.py)

- **What:** split code by responsibility: `api/` (routers) → `services/` (business rules) → `repositories/` (DB access) → `domain/` + `schemas/` (shapes), plus `core/` (config, logging).
- **Why:** one-way dependencies mean you can change the DB, the framework or a rule without rewriting everything, and services can be tested with a fake repo (no HTTP, no DB).
- **How:** router parses the request and calls a service; the service enforces rules and calls a repository; the repository is the only code that writes SQL. Wire it together once in `main.py`. Use `src/app/` layout; tests mirror `src/`.
- **When:** from day one of any service that will outlive a weekend. Don't over-layer a 3-endpoint script.
- **FDE tip:** a client's engineer should find any logic in under a minute. Predictable layout is a deliverable.

## 2. Dependency & environment management
Code: [env_check.py](../../01-backend/01-python-app-skills/02-dependency-and-env-management/practice/env_check.py)

- **What:** `pyproject.toml` declares deps, a **lockfile** pins exact versions of everything (incl. transitive), a **virtualenv** isolates the project. Tool: `uv` (fast) or poetry.
- **Why:** "works on my machine" bugs are almost always version drift. A lockfile makes dev, CI, Docker and prod identical.
- **How:** `uv add pkg` · `uv add --dev pytest ruff` · `uv sync --frozen` in CI/Docker · `uv lock --upgrade-package x` to bump deliberately · `.python-version` pins the interpreter. In Docker: copy `pyproject`+lock → install → copy code (cached layer).
- **When:** every project, at creation. Commit the lockfile. Never `pip install` into the global Python.

## 3. Configuration & settings
Code: [configuration-and-settings.py](../../01-backend/01-python-app-skills/03-configuration-and-settings/practice/configuration-and-settings.py)

- **What:** all environment-specific values (DB URL, keys, flags, ports) come from **env vars**, loaded into one typed `Settings` object (`pydantic-settings` in real projects).
- **Why:** same code runs in dev/staging/prod (12-factor); secrets stay out of git; bad config should crash at boot, not at 2 a.m. on the first request.
- **How:** `class Settings(BaseSettings)` with typed fields; required = no default; `.env` for local only (git-ignored); mask secrets in `__repr__`; create once, inject it (don't sprinkle `os.environ`).
- **When:** the moment you have a second environment or any secret. Which is always.
- **Rule:** config = changes per environment. Constants of the app logic are not config.

## 4. Structured logging
Code: [structured-logging.py](../../01-backend/01-python-app-skills/04-structured-logging/practice/structured-logging.py)

- **What:** each log line is a JSON object (`level, msg, request_id, user_id…`) written to stdout.
- **Why:** you can't debug prod by SSH-ing in. JSON is filterable/aggregatable (Datadog, Loki, CloudWatch); a **request ID** ties every line of one request together.
- **How:** a JSON `Formatter` on the root logger; set `request_id` in a `contextvars.ContextVar` in middleware, so any code, at any depth, logs it for free; `log.exception()` for errors (adds the traceback); redact `password/token/authorization`.
- **When:** every service, before the first deploy. Levels: DEBUG detail · INFO events · WARNING handled oddity · ERROR failed request · CRITICAL down. Run prod at INFO.
- **Never:** log secrets, full PII, or whole request bodies. Don't `print()` in services.

## 5. Error handling patterns
Code: [error-handling-patterns.py](../../01-backend/01-python-app-skills/05-error-handling-patterns/practice/error-handling-patterns.py)

- **What:** a small hierarchy of **domain errors** (`NotFound`, `InsufficientFunds`) kept separate from **infrastructure errors** (timeouts, 503s). Each domain error carries a status and a user-safe message.
- **Why:** users must get clear, safe messages (no stack traces/SQL); you must get full detail in logs; and retries must hit only the failures that can actually heal.
- **How:** business code raises meaningful exceptions and knows no HTTP; **one boundary** (exception handler/middleware) maps them to responses and logs once; unknown exceptions → 500 + generic message; retry transient errors with exponential backoff, capped attempts.
- **When:** always. Retry only if the call is idempotent. Fail fast on bad input/config. Never `except: pass`.
