## 6. Exception handlers
Code: [exception-handlers.py](../../01-backend/02-fastapi/06-exception-handlers/practice/exception-handlers.py)

- **What:** functions registered with `@app.exception_handler(SomeError)` that turn a raised exception into an HTTP response.
- **Why:** business code shouldn't know HTTP, and every error should look the same so clients write one parser. Unknown errors must never leak internals (`db password is hunter2`).
- **How:**
  1. A base `DomainError` carries `status`, `code` and `message`; subclasses (`OrderNotFound` 404, `PaymentDeclined` 402) set them.
  2. One handler for `DomainError` covers all subclasses.
  3. Override `RequestValidationError` (the 422), `HTTPException`, and `Exception` (the catch-all 500) so they all return `{"error": {"code", "message"}}`.
  4. The 500 handler logs the real detail and returns a generic message.
- **When:** from the first endpoint. This is yesterday-week's error-boundary pattern applied inside FastAPI.
- **Test tip:** `TestClient(app, raise_server_exceptions=False)` lets the 500 handler answer as it would in prod.

## 7. Middleware
Code: [middleware.py](../../01-backend/02-fastapi/07-middleware/practice/middleware.py)

- **What:** code that wraps every request: it runs before the handler and again after the response is built.
- **Why:** cross-cutting concerns (request ID, timing, security headers, CORS, auth gate) belong in one place, not copied into every route.
- **How:** `@app.middleware("http")` with `response = await call_next(request)`; do work before and after that line. Return a response early to short-circuit (the handler never runs). Store per-request data on `request.state`. The middleware added **last** runs **first**. `CORSMiddleware` via `app.add_middleware(...)`.
- **When:** anything that applies to all or most routes. Per-route logic (current user, DB session) uses `Depends()` instead.
- **Gotchas:** keep it fast, never read the full body in middleware (breaks streaming), and mind the ordering.

## 8. Testing FastAPI apps
Code: [testing-fastapi-apps.py](../../01-backend/02-fastapi/08-testing-fastapi-apps/practice/testing-fastapi-apps.py)

- **What:** call your app in-process with `TestClient(app)`, assert on status, body and side effects.
- **Why:** it's fast (no server, no network), it catches regressions before deploy, and it's the safety net that lets you refactor or let an AI assistant edit code.
- **How:**
  - Arrange, act, assert.
  - Swap real dependencies with `app.dependency_overrides[get_db] = fake` and clear them after each test.
  - Give every test fresh state so tests can't affect each other (real DB: roll back a transaction per test).
  - Always cover the unhappy paths: 404, 422, 401/403.
  - Use fixtures in pytest (`@pytest.fixture`); async code uses `httpx.AsyncClient` + `pytest-asyncio`.
- **When:** every endpoint gets at least a happy path and one failure test. Mostly many unit tests, some API tests like these, few end-to-end.

## How these fit
`request → middleware (id, auth gate, timing) → dependencies → handler → raises DomainError → exception handler → uniform JSON error → middleware adds headers on the way out`
Tests drive this same path with `TestClient` and fake dependencies.
