## 4. Constraints & views
Code: [constraints-and-views.sql](../../01-backend/03-databases-sql/04-constraints-and-views/practice/constraints-and-views.sql)

- **What:** rules the database enforces on every write: `NOT NULL`, `PRIMARY KEY`, `UNIQUE`, `CHECK`, `FOREIGN KEY`, exclusion. A **view** is a saved query that behaves like a table.
- **Why:** app-side validation can be bypassed (a bug, a migration script, a second service). Constraints make invalid data impossible, and the DB becomes the last line of defense.
- **How:**
  - Name your constraints (`CONSTRAINT accounts_email_format CHECK ...`) so errors are readable.
  - `CHECK` can span columns (`ended_at > started_at`). `NULL` passes a `CHECK` (unknown isn't false).
  - **FK actions:** `RESTRICT` (refuse delete; safest), `CASCADE` (delete owned children), `SET NULL` (keep child, clear link).
  - **Partial unique index:** `UNIQUE (account_id) WHERE ended_at IS NULL` = "one active subscription per account".
  - **Exclusion constraint:** no overlapping bookings per room (`EXCLUDE USING gist (room WITH =, during WITH &&)`).
  - **Add a constraint to a huge live table:** `... NOT VALID` (instant), then `VALIDATE CONSTRAINT` later without blocking writes.
  - **View:** hides complexity and exposes only safe columns; stores no data and isn't faster by itself. **Materialized view:** stores the result, fast but stale until `REFRESH MATERIALIZED VIEW CONCURRENTLY` (needs a unique index).
- **When:** invariants (must always be true) go in the DB; workflow and business policy go in the app.

## 5. Indexes
Code: [indexes.sql](../../01-backend/03-databases-sql/05-indexes/practice/indexes.sql) · runnable demo: [index_demo.py](../../01-backend/03-databases-sql/05-indexes/practice/index_demo.py)

- **What:** a separate sorted structure (B-tree by default) that lets the DB jump to rows instead of scanning the table.
- **Why:** it turns a full scan into a lookup. Measured in the demo: **~425x faster** lookups on 300k rows. The price: **~10x slower bulk inserts** with 3 indexes (every write updates every index) plus disk space.
- **How / types:**
  - **B-tree:** index columns you filter, join and sort on, plus every foreign key (Postgres doesn't index FKs for you).
  - **Composite `(a, b)`:** column order matters (leftmost prefix). Equality columns first, range/sort last. A query filtering only on `b` can't use it (demo: `SCAN`).
  - **Partial:** `WHERE status = 'failed'` indexes only the rows you query (tiny, fast).
  - **Covering:** `INCLUDE (kind)` enables index-only scans.
  - **Expression:** `(lower(email))`, and the query must use the same expression.
  - **GIN:** `jsonb @>`, arrays, full-text.
- **When the planner ignores an index:** low selectivity (a column with 3 values), a function on the column (`date(created_at) = ...`; rewrite as a range), type mismatch, leading wildcard `LIKE '%x'`, stale stats, tiny tables.
- **Production:** `CREATE INDEX CONCURRENTLY` doesn't block writes. Find unused indexes in `pg_stat_user_indexes` and drop them.

## 6. EXPLAIN ANALYZE & query tuning
Code: [explain_and_tuning.sql](../../01-backend/03-databases-sql/06-explain-analyze-and-query-tuning/practice/explain_and_tuning.sql)

- **What:** `EXPLAIN` shows the planned strategy; `EXPLAIN (ANALYZE, BUFFERS)` runs the query and shows real time, row counts and cache hits.
- **Why:** you can't tune what you can't see. Guessing at indexes is how you add useless ones.
- **How to read a plan:** innermost node outward. Watch: estimated `rows` vs `actual rows` (10x off = stale stats, run `ANALYZE`); `Rows Removed by Filter` (huge = missing index); `actual time` is per loop (× `loops`); `Execution Time` is the real number. Scan types: Seq (whole table), Index, Index Only (best), Bitmap (medium selectivity). Joins: Nested Loop (small outer + indexed inner), Hash (equality, no index), Merge (pre-sorted).
- **Tuning loop:** measure → find the slowest node → change ONE thing → measure again. Common fixes: add the missing index; rewrite function-on-column as a range; `SELECT` only needed columns; keyset instead of `OFFSET`; kill N+1 queries (JOIN / eager load); estimate `count(*)` with `pg_class.reltuples` on huge tables.
- **Safe on writes:** `BEGIN; EXPLAIN ANALYZE UPDATE ...; ROLLBACK;`.
- **Production:** `pg_stat_statements` sorted by `total_exec_time` finds the real cost (a 5 ms query run 10M times beats one 2 s report); `log_min_duration_statement` logs slow queries.

## 7. Transactions & isolation
Code: [transactions-and-isolation.sql](../../01-backend/03-databases-sql/07-transactions-and-isolation/practice/transactions-and-isolation.sql) · runnable demo: [transaction_demo.py](../../01-backend/03-databases-sql/07-transactions-and-isolation/practice/transaction_demo.py)

- **What:** a group of statements that succeeds or fails as one unit. **ACID** = Atomic, Consistent, Isolated, Durable.
- **Why:** money moves, inventory counts and multi-step writes must never be left half done, and concurrent requests must not corrupt each other.
- **Demo results:** a failed second step rolled back the first too (balances unchanged). Five concurrent "read, subtract in Python, write" withdrawals left 90 (**lost updates**); `UPDATE ... SET balance = balance - n` gave the correct 50.
- **How:**
  - **Lost update fixes (in order of preference):** atomic SQL arithmetic; `SELECT ... FOR UPDATE` (lock the row); optimistic locking (`version` column, retry when 0 rows updated). Job queues: `FOR UPDATE SKIP LOCKED`.
  - **MVCC:** readers never block writers; only writers on the same row wait.
  - **Isolation levels:** READ COMMITTED (default; each statement sees fresh commits), REPEATABLE READ (one snapshot per transaction; may need retry), SERIALIZABLE (as if one at a time; prevents write skew; retry on failure). Postgres has no dirty reads.
  - **Write skew:** two txns read the same rows, update different ones (two doctors both go off-call). Needs SERIALIZABLE or locking the rows you rely on.
  - **Deadlocks:** lock rows in a consistent order, keep transactions short, retry on error.
  - **Advisory locks:** `pg_advisory_xact_lock(key)` as a DB-backed mutex (run a cron on one instance only).
- **When / app rules:** one transaction per use-case, open late and commit early, **no network or LLM calls inside a transaction**, and always handle "serialization failure / deadlock" with a retry.
