## 1. SQLAlchemy Core
Code: [sqlalchemy-core.py](../../01-backend/04-orm-sqlalchemy/01-sqlalchemy-core/practice/sqlalchemy-core.py)

- **What:** SQL as Python objects: `Table`, `select()`, `insert()`, run through an `Engine`. No model classes. The ORM sits on top of this.
- **Why:** safe parameter binding (no SQL injection), composable queries, and one API for any database.
- **How:** `create_engine(url)` **once per process** (it owns the connection pool). `with engine.begin() as conn:` = transaction (commit on success, rollback on error); `engine.connect()` for reads. `conn.execute(insert(t), [dict, dict])` = fast bulk insert. Raw SQL only with bound params: `text("... WHERE c = :c"), {"c": v}`, never f-strings. Postgres pool tuning: `pool_size`, `max_overflow`, `pool_pre_ping=True`.
- **When:** bulk inserts, reports, and any time you want to see exactly what SQL runs. `echo=True` prints every statement.

## 2. ORM models & mappings
Code: [orm-models-and-mappings.py](../../01-backend/04-orm-sqlalchemy/02-orm-models-and-mappings/practice/orm-models-and-mappings.py)

- **What:** Python classes mapped to tables (2.x style): `class Base(DeclarativeBase)`, columns as `Mapped[type] = mapped_column(...)`.
- **Why:** one typed definition of the schema, used by your queries, your editor, and Alembic's autogenerate.
- **How:** `Mapped[str]` = NOT NULL, `Mapped[str | None]` = nullable. `Numeric(10, 2)` for money. `default=` is applied by the ORM (Python side), `server_default=func.current_timestamp()` by the database (also covers non-ORM writers). Put `UniqueConstraint`, `CheckConstraint`, `Index` in `__table_args__` and **name** them. `CreateTable(Model.__table__)` shows the DDL.
- **When:** every model. Keep constraints in the model *and* the DB, so bad data can't get in either way.

## 3. Session & unit of work
Code: [session-and-unit-of-work.py](../../01-backend/04-orm-sqlalchemy/03-session-and-unit-of-work/practice/session-and-unit-of-work.py)

- **What:** a `Session` is a workspace plus one transaction. It tracks objects (**identity map**: one Python object per row per session) and collects changes (**unit of work**).
- **Why:** you mutate attributes and call `commit()`; it works out the INSERT/UPDATE/DELETE order for you.
- **What the demo showed:** `add()` sends nothing (0 SQL); `flush()` sends the INSERT inside the transaction and assigns the `id`; `commit()` makes it permanent; two queries for the same row return the same object; changing an attribute puts it in `session.dirty` and `commit()` emits the UPDATE; `rollback()` and an exception inside `with session.begin():` both leave the data unchanged.
- **How:**
  - **Per request:** `def get_db(): with SessionLocal() as db: yield db` (this is the FastAPI dependency).
  - **`expire_on_commit`:** the default `True` reloads objects after commit. Set `False` for async code or when you return objects after committing.
  - **Rules:** never share a session across threads or requests, commit once per use-case, and never hold one open during a slow external call.
- **When:** every database interaction in the app.

## 4. Relationships & loading strategies
Code: [relationships-and-loading.py](../../01-backend/04-orm-sqlalchemy/04-relationships-and-loading/practice/relationships-and-loading.py)

- **What:** `relationship()` lets you write `author.books` instead of a join. The FK sits on the "many" side; `back_populates` links both directions. Many-to-many uses an association table (`secondary=`).
- **Why:** navigation is convenient, but **how** related rows load decides the number of queries.
- **Measured (5 authors, 10 books):**

  | Strategy | Queries | Use for |
  |---|---|---|
  | lazy (default) | 6 (1 + N) | rarely-used relations |
  | `selectinload` | 2 | collections (one-to-many, many-to-many) |
  | `joinedload` | 1 | many-to-one (`book.author`) |
  | chained selectinload | 3 | author → books → tags |

- **Cascades:** `cascade="all, delete-orphan"` for **owned** children (order → items): deleting the parent deletes them, removing one from the list deletes it. Never use it on shared things (tags).

## 5. The N+1 query problem
Code: [n-plus-one-problem.py](../../01-backend/04-orm-sqlalchemy/05-n-plus-one-problem/practice/n-plus-one-problem.py)

- **What:** 1 query for the list, then 1 more per row for a lazy relation. 100 authors cost **101 queries**; `selectinload` cost **2**.
- **Why it matters:** invisible with 5 dev rows, a slow endpoint with 5000 prod rows.
- **How:**
  - **Spot it:** `echo=True`, near-identical SELECTs in the log, or an APM trace.
  - **Fix:** `selectinload` for collections, `joinedload` for many-to-one, or one hand-written JOIN.
  - **Prevent:** `raiseload(Author.books)` (or `lazy="raise"`) makes a forgotten eager load a loud error; a **query-count test** (`assert len(queries) <= 2`) stops regressions.
- **When:** check every list endpoint that returns nested data.

## 6. Alembic migrations
Code: [alembic-migrations.py](../../01-backend/04-orm-sqlalchemy/06-alembic-migrations/practice/alembic-migrations.py)

- **What:** version-controlled schema changes: a linked list of revisions, each with `upgrade()` and `downgrade()`.
- **Why:** you can't edit a live database by hand and have staging, prod and teammates stay in sync. Migrations are the schema's git history.
- **CLI:** `alembic init` · `alembic revision --autogenerate -m "msg"` · **review the file** · `alembic upgrade head` · `alembic downgrade -1` · `alembic current` · `alembic check` (CI: fails if models and migrations drifted).
- **Autogenerate caveats:** it sees a rename as drop + add (data loss!), misses some constraints and server defaults, and never writes data migrations. The demo's diff showed exactly `add_column users.phone`.
- **Zero-downtime = expand/contract:** (1) add the new column as NULLABLE, (2) app writes both and old rows are backfilled in batches, (3) app reads only the new one, (4) drop the old column. A rename = add + copy + switch + drop, never one step. Don't add a NOT NULL column without a default to a big table (it locks it).
- **Postgres tips:** `CREATE INDEX CONCURRENTLY` inside `autocommit_block()`, and set `lock_timeout` so a migration fails fast instead of queueing behind a long query.
- **Deploy:** run `alembic upgrade head` as a release step **before** the new app version starts.
