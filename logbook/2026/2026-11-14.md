## 9. Pagination
Code: [pagination.py](../../01-backend/02-fastapi/09-pagination/practice/pagination.py)

- **What:** returning a big collection in slices instead of all at once.
- **Why:** an unbounded list kills the DB, the server memory and the client. Always cap `limit` (`Query(ge=1, le=100)`).
- **How:**
  - **Offset:** `?limit=10&offset=20` → SQL `OFFSET 20 LIMIT 10`. Simple, can jump to page N, returns a total. Slow on large tables (the DB skips rows) and unstable when rows are inserted mid-browse.
  - **Cursor (keyset):** `?limit=10&after=<cursor>` → SQL `WHERE id > :last ORDER BY id LIMIT 10`. Fast (index), stable, forward-only. Fetch `limit + 1` rows to know if there's a next page; return `next_cursor` (opaque, base64) or `null`.
- **When:** offset for admin tables and "page 3 of 8" UIs; cursor for feeds, infinite scroll, large or fast-changing data (chat history, logs, LLM run lists). The cursor key must be unique and indexed (`id`, or `(created_at, id)`).

## 10. File uploads
Code: [file-uploads.py](../../01-backend/02-fastapi/10-file-uploads/practice/file-uploads.py)

- **What:** `multipart/form-data` bodies; FastAPI gives you `UploadFile` (a spooled temp file, not bytes in RAM).
- **Why:** AI products live on uploads (PDFs, images, audio), and uploads are the classic attack surface.
- **How (four rules):**
  1. Check the real type from the first bytes (magic numbers: PNG `\x89PNG`, PDF `%PDF-`), not the filename or the client's `Content-Type`.
  2. Enforce a max size **while streaming** in chunks; delete the partial file on failure (413).
  3. Never use `file.filename` for storage: generate a UUID name (blocks `../../` path traversal).
  4. Store in object storage (S3) and keep only the key in the DB.
- **When:** any user file input. For big files, have the client upload directly to S3 with a presigned URL, and set a body limit at the proxy (`client_max_body_size`). Needs `python-multipart` installed. Status codes: 415 wrong type, 413 too large.

## 11. Background tasks
Code: [background-tasks.py](../../01-backend/02-fastapi/11-background-tasks/practice/background-tasks.py)

- **What:** `background.add_task(fn, *args)` runs a function after the response is sent, in the same process.
- **Why:** the user shouldn't wait for slow side effects (email, audit log, cache warm-up).
- **How:** inject `BackgroundTasks`, do the essential work and commit first, then queue the extras. Tasks run in order. Give them their own DB session (the request's is already closed).
- **When, and when not:** best-effort, fast, loss-tolerable work only. It has **no retries, no persistence, and dies with the process**. Anything that must not be lost, is heavy, needs retries or should scale separately goes to a real queue (Redis + RQ/Celery, section 08). Make tasks idempotent.

## Decision cheat-sheet
| Situation | Use |
|---|---|
| Admin table with page numbers | offset pagination |
| Infinite scroll / big changing data | cursor pagination |
| User uploads a PDF | sniff type, stream with size cap, store in S3 |
| Send a welcome email, don't block signup | `BackgroundTasks` |
| Process the PDF with an LLM (slow, must not be lost) | queue + worker |
