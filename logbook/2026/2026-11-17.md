## 1. PostgreSQL basics
Code: [postgres-basics.sql](../../01-backend/03-databases-sql/01-postgres-basics/practice/postgres-basics.sql)

- **What:** the relational database you'll use for nearly every backend. Tables of typed rows, queried with SQL.
- **Why:** it gives you correctness (types, constraints, transactions) plus enough flexibility (`jsonb`, arrays) that it covers most needs without extra databases.
- **How:**
  - **Types to use:** `bigint GENERATED ALWAYS AS IDENTITY` (id), `uuid` (public ids), `text`, `numeric(10,2)` (money, never float), `boolean`, `jsonb`, `timestamptz` (always, not plain `timestamp`).
  - **CRUD:** `INSERT ... RETURNING` (get generated ids back), `SELECT ... WHERE/ORDER BY/LIMIT`, `UPDATE`/`DELETE` (run the `WHERE` as a `SELECT` first), upsert with `ON CONFLICT (col) DO UPDATE SET x = EXCLUDED.x`.
  - **jsonb:** `->` json, `->>` text, `@>` contains. Arrays: `'x' = ANY(tags)`.
  - **NULL = unknown:** `NULL = NULL` is not true; use `IS NULL` / `IS DISTINCT FROM`; `COALESCE` for defaults; `count(col)` skips NULLs; `NOT IN` with a NULL returns nothing, so use `NOT EXISTS`.
  - **psql:** `\dt` tables, `\d table` describe, `\x` expanded view, `\timing`, `\c db`, `\q`.
- **When:** default choice. Reach for `jsonb` only for truly free-form attributes, not to dodge schema design.

## 2. Schema design & normalization
Code: [schema_design.sql](../../01-backend/03-databases-sql/02-schema-design-and-normalization/practice/schema_design.sql)

- **What:** deciding the tables, keys and relationships so each fact is stored once.
- **Why:** a bad schema is the most expensive thing to fix later (migrations on live data) and causes duplicated, contradictory data.
- **How:**
  1. List entities (nouns) → decide relationships: 1:N puts the FK on the "many" side; N:M needs a junction table (`memberships`, `project_tags`) whose extra columns describe the relationship.
  2. Keys: surrogate PK (`bigint` identity or `uuid`) + natural keys (`email`, `slug`) as `UNIQUE`.
  3. Normalize: 1NF no packed values (no `tags_csv`), 2NF/3NF no repeated facts (org name lives only in `orgs`).
  4. Constraints do the policing: `NOT NULL`, `CHECK`, `FK ... ON DELETE CASCADE / SET NULL`, composite `UNIQUE (org_id, name)`.
  5. **Soft delete:** `deleted_at` column + a *partial* unique index (`WHERE deleted_at IS NULL`).
  6. **Multi-tenancy:** `org_id` on every tenant-owned table and in every query.
  7. **Postgres does not auto-index FKs**: add `CREATE INDEX` on them yourself.
- **When to denormalize:** only after measuring a read problem (cached counts, immutable snapshots like an invoice's address-at-the-time). Keep the source of truth.
- **FDE angle:** modeling a customer's messy data into clean tables is your week-one job.

## 3. Joins
Code: [joins.sql](../../01-backend/03-databases-sql/03-joins/practice/joins.sql) (runs on Postgres and SQLite)

- **What:** combining rows from tables by matching columns.
- **Why:** normalized data lives in many tables; joins reassemble it for queries and reports.
- **How:**
  - `INNER JOIN`: only matching rows. `LEFT JOIN`: all left rows, NULLs where no match (use `WHERE right.id IS NULL` for "has no X"). `FULL OUTER`: everything from both (reconciliation). `CROSS`: all combinations. **Self join**: employee → manager.
  - **Gotcha 1:** a `WHERE` filter on the right table of a `LEFT JOIN` turns it into an inner join; put it in `ON`.
  - **Gotcha 2, fan-out:** joining a 1:N table multiplies rows, so `SUM` over the result double counts (530 instead of 430). Aggregate the many-side first, then join.
  - `GROUP BY` + `HAVING` (filter groups; `WHERE` filters rows before grouping).
  - **CTEs** (`WITH x AS (...)`) make multi-step queries readable. `EXISTS` for "has any matching row".
  - **Window functions** compute across rows without collapsing them: `sum() OVER (PARTITION BY ...)`, `row_number()` for top-N-per-group (latest order per customer), running totals with `OVER (ORDER BY ...)`.
- **When:** daily. Top-N-per-group and "who has none" are the two patterns you'll reuse the most.
