## 15. API versioning
Code: [api_versioning.py](../../01-backend/02-fastapi/15-api-versioning/practice/api_versioning.py)

- **What:** a way to change your API while clients who depend on the old shape keep working.
- **Why:** once other people's code calls you (customer integrations, mobile apps you can't force-update), a renamed field breaks them in production.
- **How:**
  - **Non-breaking, no new version:** add an endpoint, add an optional request field, add a response field.
  - **Breaking, needs a new version:** rename/remove a field, change a type or meaning, make something required.
  - **URL versioning:** `APIRouter(prefix="/v1")` and `/v2`; the most common, visible and easy to route. (Header versioning: cleaner URLs, harder to debug.)
  - Share the business logic between versions; only the schemas differ.
  - **Retire the old one:** `deprecated=True` on the route, response headers `Deprecation: true`, `Sunset: <date>`, `Link: <...>; rel="successor-version"`.
- **When:** prefer additive changes so you rarely need v2. When you do, keep live versions few: each one is code to test, secure and support. Remove v1 only after the sunset date, once its traffic is near zero (log the version per client).

## 16. OpenAPI & Swagger
Code: [openapi_contract.py](../../01-backend/02-fastapi/16-openapi-and-swagger/practice/openapi_contract.py)

- **What:** FastAPI generates `/openapi.json` (OpenAPI 3.1), a machine-readable contract of every route, parameter, schema and response. `/docs` (Swagger UI) and `/redoc` render it.
- **Why:** it's the single file customer engineers, frontend codegen, Postman and API gateways consume. A good contract means fewer support questions and no hand-written client code.
- **How:**
  - Set `title`, `version`, `description` and tags on the app.
  - `operation_id="createInvoice"` gives generated clients clean method names.
  - `responses={404: {"model": ErrorOut}}` documents the non-200 outcomes.
  - `Field(description=..., examples=[...])` documents fields.
  - Export the spec and commit it so PR diffs show API changes.
  - Generate a typed TS client: `npx openapi-typescript openapi.json -o api.d.ts` (types) or `npx orval` (client + React Query hooks).
  - Contract-test with `schemathesis` or a CI diff on the spec.
- **When:** from the first endpoint. For private services you can hide docs with `docs_url=None`.
- **FDE angle:** you hand the spec to a customer's engineers on day one, and they generate their own client from it.

## FastAPI section recap (16 topics)
| Area | One-line takeaway |
|---|---|
| Routing, request/response models, validation | Signature = contract; Pydantic validates in, filters out |
| Dependency injection | Share logic with `Depends`; swap it in tests |
| Exception handlers, middleware | One error shape; cross-cutting code in one place |
| Testing | `TestClient` + overrides + fresh state per test |
| Pagination, uploads, background tasks | Cap everything; sniff + stream files; queues for important work |
| Streaming, WebSockets, rate limiting | SSE for tokens; WS for two-way; 429 + Retry-After |
| Versioning, OpenAPI | Additive changes; the spec is your product's contract |
