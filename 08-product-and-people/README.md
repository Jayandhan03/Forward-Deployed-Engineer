# 08 · Product & People

Past a certain point, code is not the bottleneck — judgment and communication are. This is what
separates an engineer who closes tickets from one who builds products people use. Treat it as a set
of habits that compound, not a checklist you finish.

**Depth target:** L3, ongoing. **Budget:** ~1–2 concentrated weeks; the rest by doing.

---

## 00-product-thinking

- [ ] MVP — the smallest thing that tests the riskiest assumption (not "v1 with fewer features")
- [ ] Product‑market fit — what it feels like, what signals precede it
- [ ] User interviews — asking without leading; the "Mom Test"
- [ ] Metrics, funnels, retention — activation, retention curves, the one metric that matters now
- [ ] A/B testing — hypothesis, sample size, significance, when not to bother
- [ ] Pricing — value‑based, tiers, usage vs seat, the psychology
- [ ] Feature prioritization — RICE / impact‑effort; saying no; the cost of every feature you keep

## 01-ui-ux

Enough to make a product feel premium without a designer.

- [ ] Typography — scale, line length, hierarchy, 2 typefaces max
- [ ] Color — a restrained palette, semantic tokens, contrast
- [ ] Spacing & layout — an 8px grid, whitespace, alignment, visual rhythm
- [ ] Accessibility — keyboard, focus states, contrast, ARIA where needed, motion‑reduce
- [ ] UX flows — reduce steps, sensible defaults, forgiving errors, empty/loading/error states
- [ ] Design systems — tokens → primitives → components → patterns

## 02-working-with-humans

- [ ] Writing clearly — PRs, docs, tickets precise enough to not need a follow‑up meeting
- [ ] Estimation & scoping — turn an ambiguous ask into something you can commit to and be right about
- [ ] Agile & Scrum basics — sprints, standups, backlogs; the shared vocabulary
- [ ] Reading unfamiliar code — navigate a codebase you didn't write without the author in the room
- [ ] Code review culture — feedback that improves the code; receiving it without ego
- [ ] Mentoring — once past mid‑level, your impact stops being just your own output

## 03-the-long-game

Never fully checked off — that's the point.

- [ ] Build real projects — one finished side project teaches more than ten tutorials
- [ ] Read other people's code — study a mature open‑source codebase, see how trade‑offs got made
- [ ] Ship and get feedback — real usage reveals what no to‑do app ever will
- [ ] Depth in one area, breadth everywhere else — be the go‑to on something; stay conversant in the rest
- [ ] Know what you don't know — the senior/junior gap is mostly knowing which question to ask

---

## Habits to run continuously

- Write a one‑paragraph "why" before starting any feature.
- Every project gets a real README: what, why, how to run, decisions, trade‑offs.
- Ship something small every week; put it in front of a real person.
- Once a month, read one PR or module from a codebase you admire and take notes.

## Done when

This domain doesn't get "done." You're on track when your PRs need no follow‑up meeting, your
estimates land, your side projects have real users, and you can explain a past architecture decision
in terms of what it cost.
